# 移动端纯前端语义分割功能的关键问题与解决方案

> 本文档整理“视界”图片编辑应用中 AI 区域滤镜功能的工程实践，重点记录在
> uni-app + Android WebView 环境下落地纯前端语义分割时遇到的问题、原因分析、
> 解决措施与验证数据，可直接作为毕业论文“系统实现”“关键技术”或“测试与分析”
> 章节的素材。

## 1 问题背景与系统约束

### 1.1 功能目标

AI 区域滤镜要求用户在手机相册中选择一张图片后，在设备本地完成语义分割，
将画面划分为若干语义区域，并允许用户对每个区域独立套用滤镜。整个流程不上传
图片，不依赖后端服务。

### 1.2 技术方案

- 前端框架：uni-app（Vue 3 + TypeScript），运行于 Android App 的 WebView。
- 绘制与推理：renderjs + Canvas 2D + ONNX Runtime Web 1.29.0。
- 推理后端：WebAssembly 单线程（`numThreads = 1`，`proxy = false`）。
- 分割模型：SegFormer-B0 语义分割模型，约 14.6 MB 的 ONNX 文件，输入名
  `pixel_values`，输出名 `logits`，输出通道数为 150，对应 ADE20K 数据集的
  150 个类别。模型输入的空间维度为动态维度，输出空间尺寸为输入的 1/4。
- 模型结构确认：ONNX 文件由 PyTorch 2.14 导出，未写入模型名称元数据；
  通过解析 initializer 可确认编码器为 MiT-B0（各级 embedding 维度为
  32 / 64 / 160 / 256），分类头形状为 `[150, 256, 1, 1]`，总参数量为
  3,752,438。该配置与 Hugging Face 的
  `nvidia/segformer-b0-finetuned-ade-512-512` 一致。

### 1.3 平台约束

uni-app 的 App-vue 架构中，逻辑层没有 DOM、Canvas 和 Worker，无法直接运行
ONNX Runtime Web；renderjs 运行在 view WebView 中，虽然具备完整 DOM 能力，
但不能调用 uni API，也不能直接读写逻辑层状态。这一“双层运行时”是后续多个
问题的根源。

## 2 运行环境与架构问题

### 2.1 renderjs 与逻辑层的通信约束

**现象。** 推理代码无法在普通 `<script setup>` 中访问 Canvas；组件编译后
renderjs 模块不生效。

**原因。** Vue 3 的 `<script setup>` 不支持 renderjs 模块声明；renderjs 只能
写在 Options API 组件中。此外，renderjs 与逻辑层处于不同运行时，不能共享
响应式状态。

**解决方案。**

1. 含 renderjs 的组件统一使用 Options API。
2. 逻辑层 → renderjs：将参数序列化为 JSON 字符串，通过 prop 传入，并用
   `:change:ai-payload` 监听变化触发 renderjs 方法。
3. renderjs → 逻辑层：通过 `ownerInstance.callMethod('方法名', 数据)` 回传，
   被调用的方法必须定义在逻辑层组件的 `methods` 中。

该约束决定了系统采用“逻辑层管理状态、renderjs 执行绘制与推理”的分工，
后续所有跨层数据都通过轻量 payload 传递，避免在 renderjs 中直接操作业务状态。

### 2.2 画布宿主对象类型异常

**现象。** 自检完成后选择本地图片，控制台报：

```text
TypeError: host.querySelector is not a function at uni-app-view.umd.js:7
```

此后没有任何图片读取或推理日志。

**原因。** 在 App 端 renderjs 中，`this.$el` 或 `document.getElementById()`
在特定时机返回的并不是真实 DOM，而是 uni-app 的包装对象。该对象非空，
但缺少 `querySelector`、`appendChild`、`getBoundingClientRect` 等方法，
因此仅用 `if (!host)` 无法拦截。

**解决方案。**

```js
isDomHost(el) {
  return !!el &&
    typeof el.querySelector === 'function' &&
    typeof el.appendChild === 'function' &&
    typeof el.getBoundingClientRect === 'function'
}
```

当 `$el` 不满足上述条件时，回退到 `document.querySelector('.ai-canvas-stage')`；
`ensureCanvas` 整体包在 `try/catch` 中，画布初始化失败不会阻断后续图片读取。
自检页采用同样策略，并在类型异常时打印实际对象类型，便于定位。

**启示。** 跨运行时获取 DOM 时，不能只判断空值，应进行能力检测（duck typing），
并为关键初始化流程提供异常隔离。

### 2.3 交互事件与画布手势冲突

**现象。** 画布单击选区和双击缩放互相干扰。

**解决方案。** 单击延迟 300 ms 执行，若期间检测到双击则取消待执行的单击；
双击在 1× 与 2× 之间切换。该问题与推理无关，但会影响区域选择的准确性，
因此在实现点选功能时一并处理。

## 3 静态资源与图片加载问题

### 3.1 大文件读取挂起

**现象。** 真机自检日志停在 `ORT 版本: 1.29.0` 之后，既不报错也不继续，
界面长期无响应。

**原因。** 原实现使用 `plus.io.FileReader.readAsArrayBuffer()` 一次性读取
13.3 MB 的 WASM 与 14.6 MB 的模型。在 Android 上，`readAsArrayBuffer` 需要
把数据从 native 层经 JS 桥整体传回，大文件读取实测可能一直不触发
`onloadend`；旧代码既没有超时也没有进度日志，因此表现为“静默挂起”。

**解决方案。**

1. 通过 `File.slice(offset, end)` 按 512 KB 分块读取；`File.slice` 不可用时
   回退到 `Blob.prototype.slice.call`。
2. 每个分块新建一个 `plus.io.FileReader`，读取完成后拼入 `Uint8Array`。
3. 每个分块设置 15 s 超时，超时调用 `abort()` 并抛出明确错误。
4. 分块之间使用 `setTimeout(0)` 让出事件循环，避免阻塞 UI。
5. 每完成约 25% 输出一次进度日志。
6. 路径解析设置 6 s 超时，并按 `_www/` 前缀、原路径、去 `./` 前缀、
   `file:///` 前缀等候选依次尝试。

**实测结果。** 测试机型为 Android 14。其 `plus.io.File` 不支持 `slice`，
分块方案在该机型上记录 `plus.io File.slice 不可用，无法分块读取`；`fetch`
读取本地 `file://` 资源被 WebView 拒绝，记录 `Failed to fetch`；最终由
`XMLHttpRequest` 成功读取，WASM 耗时 183 ms，模型耗时 204 ms。该结果说明：
**多级回退与明确日志比单一“最优”读取方式更重要**。

### 3.2 Android 分区存储导致相册原图不可读

**现象。** 用户选择相册图片后，等待 15 s 才出现：

```text
plus.io 分块读取图片失败，尝试 DataURL: plus.io 分块读取超时
```

**原因。** Android 10 及以上采用分区存储，相册返回的原始路径对应用而言
不是可直接读取的文件路径。`readAsDataURL` 与 `readAsArrayBuffer` 均可能
永不回调；`File.slice()` 切片的 `fullPath` 仍指向原文件，分块读取对相册原图
同样无效。

**解决方案。** 在逻辑层调用 `uni.compressImage`，由原生侧读取原图、压缩并
写入应用自己的临时目录，再把临时路径交给 renderjs。压缩质量设为 95，
减少 JPEG 压缩对物体边缘的破坏。

**进一步优化。** 渲染层读取图片时改为 DataURL 优先：压缩后的图片通常只有
几百 KB，`readAsDataURL` 在该机型上 47 ms 即可完成，而 `readAsArrayBuffer`
可能一直不回调。读取顺序调整为：

1. `plus.io` DataURL；
2. `plus.io` 分块 ArrayBuffer + Blob URL；
3. `convertLocalFileSystemURL` 生成的本地 URL；
4. 原路径直接交给 `Image`。

每一级失败都记录具体原因，最终失败才进入错误浮层。

### 3.3 跨源画布与 `getImageData`

**现象。** 部分图片以 `file://` 直接加载后，引导滤波读取画布像素时抛出
安全异常，导致整个识别流程中断。

**原因。** 当图片被 WebView 视为跨源资源时，Canvas 被标记为“污染”，
`getImageData` 被禁止。

**解决方案。** 在 `grayscaleGuide` 中对 `getImageData` 加 `try/catch`。
失败时记录日志并返回 `null`，细化流程整体回退到低分辨率粗蒙版，不影响
区域识别、风格合成和用户操作。

## 4 模型输入输出与后处理问题

### 4.1 动态维度与元数据不一致

**现象。** 创建会话后，ONNX Runtime 打印：

```text
Expected shape ... does not match actual shape ...
```

**原因。** 模型元数据声明的输出形状为 `[1, 150, 56, 56]`，与实际推理结果
不符。实际输出空间尺寸是模型输入的 1/4：

| 输入尺寸 | 输出形状 |
| --- | --- |
| 512 × 512 | `[1, 150, 128, 128]` |
| 768 × 768 | `[1, 150, 192, 192]` |
| 1024 × 1024 | `[1, 150, 256, 256]` |

**解决方案。** 不依赖静态元数据，所有后处理均从运行时 `output.dims` 读取
`numClasses`、`outH`、`outW`。元数据不一致警告保留在日志中，作为已知现象。

### 4.2 输出语义不确定：logits、softmax 还是 sigmoid

**现象。** 不同导出方式的模型输出可能是原始 logits、softmax 概率或逐类别
sigmoid 概率，直接按同一种方式处理会导致引导滤波的输入尺度错误。

**解决方案。** 对输出抽样最多 64 个像素 × 150 个类别：

- 若所有值都落在 `[-0.001, 1.001]`，视为概率，直接使用；
- 否则视为 logits，按像素做数值稳定 softmax：

```text
p_c = exp(z_c - max(z)) / sum_k exp(z_k - max(z))
```

同时不要求各类别概率之和严格为 1，以兼容逐类别 sigmoid 输出。

### 4.3 低分辨率输出的边缘块状效应

**现象。** 模型输出仅为输入的 1/4，若直接把类别索引双线性放大到工作分辨率，
区域边界呈现明显的网格状台阶。

**原因。** 对类别索引做插值在语义上不成立：类别编号是离散标签，插值结果没有
概率意义。

**解决方案。** 采用“类别候选 + 分数双线性”策略：

1. 对低分辨率 logits 逐像素取 `argmax`，得到类别候选；
2. 对每个输出像素，取周围 4 个低分辨率像素的候选类别；
3. 用 logits 对每个候选类别做双线性加权评分，取得分最高者；
4. 使用 3 × 3 多数滤波平滑孤立噪点。

该方法避免了直接插值类别编号，但受限于 1/4 分辨率和 3 × 3 多数滤波，
边界仍然只能达到低分辨率网格级别，因此还需要引导滤波进行精细化的第二步。

区域统计阶段另外设置 1% 的面积阈值：占比低于该比例的零碎区域不进入展示列表。
这样既避免噪点占满区域栏，也减少不必要的引导滤波计算。最终展示的区域数量按
实际有效区域计算，不强制补足固定数量。

## 5 分割边界精细化

### 5.1 问题描述

模型输出的低分辨率类别图即使经过分数双线性细化，边界仍会出现块状或锯齿，
区域风格覆盖后能明显看出“蒙版边缘”与真实物体轮廓不重合。用户对首版效果的
反馈是“边界非常粗糙”。

仅提高推理分辨率可以缓解问题，但代价是推理时间与内存按面积增长；在移动端
WebView 中，分辨率不能无限提高。因此系统采用“保持可接受的推理分辨率 +
后处理引导滤波 + 提高工作分辨率”的组合方案。

### 5.2 引导滤波原理

引导滤波假设在局部窗口内，输出 `q` 与引导图 `I` 成线性关系：

```text
q_i = a_k * I_i + b_k,  i ∈ ω_k
```

其中 `a_k`、`b_k` 在窗口 `ω_k` 内为常数。通过最小化输出与输入 `p` 的差异，
可得：

```text
a_k = cov(I, p) / (var(I) + ε)
b_k = mean(p) - a_k * mean(I)
```

再对 `a_k`、`b_k` 做窗口平均，得到最终输出。引导图采用原图灰度
（`0.299R + 0.587G + 0.114B`），输入 `p` 为某一类别的概率图。

- 当局部区域纹理复杂、方差大时，`a` 接近 1，输出主要跟随原图边缘；
- 当局部区域平坦、方差小时，`a` 接近 0，输出接近局部平均概率。

因此，引导滤波能够在保持概率平滑的同时，让蒙版边界贴合原图中的真实轮廓。

### 5.3 快速引导滤波与工程实现

直接在 1024 × 1024 工作分辨率上为 12 个区域分别做引导滤波，计算量较大。
系统采用快速引导滤波（Fast Guided Filter）：

1. 在低分辨率（模型输出，256 × 256）上计算每个类别的概率 `p`；
2. 在低分辨率上计算 `mean(I)`、`var(I)`、`mean(p)`、`mean(I·p)`；
3. 得到低分辨率系数 `a`、`b`；
4. 对 `a`、`b` 做窗口平均后，双线性放大到工作分辨率；
5. 在工作分辨率上计算 `q = a * I + b`。

盒式窗口均值通过积分图实现，时间复杂度为 `O(N)`，与窗口半径无关：

```text
S(x, y) = S(x-1, y) + S(x, y-1) - S(x-1, y-1) + I(x, y)
```

积分图使用 `Float64Array`，避免 1024² 量级累加时的浮点精度损失。

最终将 `q` 转为蒙版 alpha：

```text
t = clamp((q - 0.47) / 0.06, 0, 1)
alpha = round(smoothstep(t) * 255)
```

0.47–0.53 的窄过渡带只保留约 1–2 个工作像素的抗锯齿过渡。过渡带过宽会让
风格覆盖出现大范围半透明渐变，看起来“发虚”；过窄则容易产生锯齿。该区间
经过真机反馈后由最初的 0.35–0.65 收窄而来。

### 5.4 参数调整与分辨率升级

首版引导滤波使用 `REFINE_RADIUS = 4`、`REFINE_EPS = 0.01`、过渡带
0.35–0.65。真机反馈边界仍然模糊后，进行了如下调整：

| 参数 | 首版 | 调整后 | 作用 |
| --- | --- | --- | --- |
| `REFINE_RADIUS` | 4 | 3 | 减小低分辨率窗口，更多保留局部边缘 |
| `REFINE_EPS` | 0.01 | 0.0025 | 降低正则项，使系数更跟随引导图 |
| alpha 过渡带 | 0.35–0.65 | 0.47–0.53 | 收窄半透明区域，边界更锐利 |
| 推理输入 | 512 | 768 → 1024 | 提高低分辨率概率图的空间密度 |
| 工作分辨率 | 768 | 1024 | 提高蒙版与合成的像素精度 |
| 源图最长边 | 1024 | 1536 | 保留更多引导图细节 |
| 图片压缩质量 | 85 | 95 | 减少 JPEG 压缩对边缘的破坏 |

推理输入提升到 1024 后，模型输出为 256 × 256，相对于 512 输入的 128 × 128
提升了 4 倍像素；引导滤波的输入网格随之变密，`a`、`b` 系数放大到 1024 工作
分辨率后，边界可以跟随更细的原图轮廓。

### 5.5 推理尺寸的自适应回退

部分 ONNX 导出模型虽然标记了动态维度，实际只接受较小的输入尺寸；不同机型
的可用内存也不同。系统采用级联尝试：

```text
1024 × 1024 → 768 × 768 → 512 × 512
```

每次尝试失败都记录原因，成功后把该设备的可用尺寸写入 `inferSize`，后续图片
直接使用可用档位，避免重复失败。该机制把“模型/设备能力差异”从致命错误
转化为可降级的性能差异。

### 5.6 内存与性能权衡

1024 输入是本方案在手机 WebView 中的实际上限，原因不是加载时间，而是内存：

- 输入张量为 `3 × 1024 × 1024 × 4 B ≈ 12 MB`；
- 输出张量为 `150 × 256 × 256 × 4 B ≈ 39 MB`；
- Transformer 类模型的注意力矩阵与中间特征图随空间尺寸近似平方增长，
  峰值内存可达数百 MB；
- 工作分辨率 1024 下，单个 RGBA 蒙版画布约 4 MB，多个缓存叠加后内存压力
  进一步增加。

如果继续提升到 1536，风险将从“更慢”变为“WebView 被系统直接终止”，而这类
崩溃无法通过 `try/catch` 回退。因此系统选择 1024 作为画质与稳定性的平衡点，
并通过以下方式控制内存：

1. 只预计算前 12 个区域的 alpha，蒙版画布按需创建；
2. 蒙版画布缓存设置上限（14 个），超出后按创建顺序淘汰；
3. 强度变化时清理滤镜画布缓存，避免拖动滑杆产生大量中间画布；
4. 推理失败时自动降档，而不是继续占用内存重试。

## 6 蒙版可视化问题

### 6.1 相邻类别颜色近似

**现象。** 画布上的区域蒙版看起来是一片相近颜色的模糊色块，难以区分区域。

**原因。** 首版类别色相采用 `id * 360 / 150`，相邻类别 id 的色相只相差
2.4°，人眼几乎无法区分；多个区域叠加后更像一片低对比度色块。

**解决方案。** 使用黄金角散列生成色相：

```text
hue = (id * 137.508) mod 360
```

黄金角可以让相邻 id 的色相在圆周上尽量分散，同时保持颜色稳定、可复现。
饱和度与亮度再根据 id 做小幅偏移，进一步增加区分度。

### 6.2 蒙版透明度与绘制顺序

**问题。** 提示色过淡时用户看不清；过浓又会遮挡原图细节。

**解决方案。**

- 选中区域 alpha = 112，其他区域 alpha = 52（0–255）；
- 选中区域最后绘制，避免被相邻区域的提示色覆盖；
- 蒙版仅在 AI 工具内、非对比、非预览、识别完成时显示；
- 区域风格覆盖使用 `destination-in` 将风格图裁剪到蒙版内，再叠加到合成画布，
  保证区域之间互不污染。

### 6.3 点选与蒙版的一致性

画布点选优先读取细化后的 `maskAlphaCache`：只有当某区域在该像素的 alpha
大于等于 64 时才判定命中，否则回退到粗分割 mask。这样既利用了细化蒙版的
边界精度，又避免了细化失败时无法点选。

## 7 工程可诊断性

移动端 WebView 缺少方便的调试工具，因此系统把“可诊断”作为实现要求：

1. **分阶段日志。** 图片读取、资源读取、会话创建、推理、argmax、双线性细化、
   多数滤波、引导细化、合成分别输出耗时与结果。
2. **细化结果可量化。** 日志输出 `蒙版引导细化 Xms，区域 refinedCount/topIds.length 个`，
   例如 `6/6`，可以直接判断是否发生回退。
3. **回退链路可追踪。** 每种读取方式失败都记录具体原因，而不是只报最终错误。
4. **独立自检页。** 可查看 `window.plus`、WebAssembly、Canvas filter、资源
   读取方式、会话与推理耗时，并支持复制日志。
5. **区分“假失败”。** 日志中的 `plus.io File.slice 不可用`、`Failed to fetch`
   是回退尝试，不是最终失败；以最后一条“读取成功”与“自检通过”为准。

## 8 实测数据

以下数据采集自 Android 14 真机，除特别说明外均为 512 × 512 输入版本。
768 与 1024 档位在本文档整理时尚未完成真机计时，表中给出理论增长区间，
最终以实际日志为准。

| 阶段 | 实测值 |
| --- | --- |
| WASM 读取（XHR） | 183 ms |
| 模型读取（XHR） | 204 ms |
| InferenceSession 创建 | 496 ms |
| 推理（自检合成图，512 输入） | 2113 ms |
| 推理（真实图片，512 输入） | 2199 ms |
| 小图 argmax | 23 ms |
| 双线性细化 | 68 ms |
| 多数滤波 | 90 ms |
| 蒙版引导细化（6 个区域） | 597 ms |
| 分割总计（真实图片） | 3006 ms |
| 图片 DataURL 加载 | 47 ms |
| 图片尺寸 / 工作尺寸 | 1024 × 1024 / 768 × 768 |

耗时增长趋势：

- 768 输入约为 512 输入的 2–2.5 倍；
- 1024 输入约为 512 输入的 4–5 倍；
- 引导滤波耗时与区域数近似线性，与工作分辨率近似线性（积分图实现）。

需要强调的是，上述耗时包含模型读取、会话创建、推理与后处理全流程；首次识别
还包含约 28 MB 静态资源的读取。实际用户体验应结合“首次加载”和“后续分割”
两个阶段分别评价。

## 9 经验总结

1. **跨层架构要先建立最小闭环。** uni-app 逻辑层与 renderjs 的通信约束、
   DOM 宿主类型、Options API 限制，任何一个判断错误都会让后续工作全部失效。
   先验证“取到画布 → 画一个像素 → 回传一个值”，再接入模型。
2. **所有跨桥异步读取都必须有超时。** Android WebView 的 `plus.io` 读取可能
   既不成功也不失败。没有超时和进度日志，故障就表现为“静默卡死”，比报错更
   难定位。
3. **多级回退优于单一方案。** 同一台设备上，`File.slice`、`fetch`、XHR 的可用
   性并不一致；把可用性探测、超时和回退链路做进代码，才能覆盖机型差异。
4. **后处理的收益可能高于换模型。** 在推理分辨率受限的前提下，引导滤波把
   低分辨率概率图与高分辨率原图结合，显著改善了边界，而模型体积和推理成本
   没有增加。
5. **分辨率提升受内存约束，而非仅受时间约束。** 移动端 WebView 的内存上限
   会让高分辨率推理从“慢”变成“崩溃”，因此需要级联回退和明确的上限。
6. **可视化映射要按人眼感知设计。** 类别颜色不能线性分配色相；黄金角散列、
   透明度分层和绘制顺序都会直接影响用户对分割质量的判断。
7. **日志要能区分“回退”和“失败”。** 否则用户会把正常的回退尝试当成故障，
   增加无效沟通与排查成本。
